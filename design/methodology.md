AgentWiki 项目方法论与实施路线图

核心理念：目标锚定 + 分层验证 + 渐进交付

三大原则

1. 目标锚定：每个决策都回溯到用户场景，不为了技术而技术
2. 分层验证：每层设计必须经过"定义 - 评审 - 原型 - 测试"四步
3. 渐进交付：每 2 周一个可演示的里程碑，不追求一步到位

第一部分：问题解决方法论

1.1 遇到细节不清楚时的标准流程

步骤 1：定义问题
- 这个细节影响什么用户场景？
- 不解决会有什么后果？
- 解决后能带来什么价值？

步骤 2：查找参考
- 看 Docmost/Outline 怎么处理的？
- 看 SwarmVault/Mnemon 怎么处理的？
- 看行业最佳实践（GitHub、Notion、Confluence）
- 记录参考来源和决策理由

步骤 3：提出方案
- 方案 A：简单实现，快速验证
- 方案 B：完整实现，长期可用
- 方案 C：暂不实现，标记为 TODO

步骤 4：决策标准
- 是否阻塞当前里程碑？
- 改动成本 vs 收益？
- 是否影响架构一致性？
- 是否可以后续无痛升级？

步骤 5：记录决策
- 写入 decisions.md（决策日志）

1.2 决策日志模板

日期：2024-01-15（历史说明性决策日志示例，不构成当前任务）

问题：Agent 编辑页面时，是否需要实时锁机制？

背景：
- 人类用户通过 Yjs 协作编辑，天然支持并发
- Agent 通过 API 编辑，可能和人类同时操作同一页面

参考：
- Docmost：使用 Yjs 的 CRDT，无锁，自动合并
- Notion：乐观锁，版本号冲突时提示用户
- Confluence：页面级锁，编辑时锁定

方案对比：

方案 | 实现成本 | 用户体验 | 一致性 | 选择
A. Yjs CRDT（无锁） | 低 | 好 | 最终一致 | 选中
B. 乐观锁（版本号） | 中 | 中 | 强一致 |
C. 悲观锁（页面锁） | 高 | 差 | 强一致 |

决策：选择方案 A

理由：
1. Yjs 已经集成，无需额外开发
2. Agent 编辑通常是非交互式的，自动合并可接受
3. 如果冲突严重，可通过 lint 检测并提示

风险：
- Agent 批量编辑可能产生大量冲突 - 通过队列串行化处理

示例后续行动：
- 示例后续行动：在 Agent 编辑 API 中加入 Yjs awareness
- 示例后续行动：添加冲突检测和通知机制
- 示例后续行动：记录到技术债务清单

第二部分：分阶段实施路线图

2.1 总体阶段划分

Phase 0: 基础准备 (1 周)
- 环境搭建：Docker、PostgreSQL、Redis
- 脚手架：NestJS + Next.js + Prisma
- 代码规范：ESLint、Prettier、Commit 规范
- 输出：可运行的空项目 + CI/CD 流水线

Phase 1: 核心骨架 (2-3 周)
- 用户认证：注册/登录/SSO
- 空间管理：创建/列表/成员
- 页面 CRUD：创建/读取/更新/删除
- Markdown 编辑器：基础编辑 + 预览
- 输出：可自托管的极简 Wiki

Phase 2: Agent 接入 (2-3 周)
- Agent 管理：CRUD + API Key 生成
- Agent 认证：API Key + Secret 验证
- Agent 权限：Scope + 操作权限检查
- 审批流程：Agent 提交 - 人类审批
- 输出：Agent 能读写 Wiki，人类能审批

Phase 3: 知识增强 (3-4 周)
- 页面类型：concept/entity/decision/fact/procedure
- YAML Frontmatter：标签、实体、置信度
- 知识图谱：边表 + 基础查询
- 相关页面推荐：基于图谱关联
- 输出：页面有类型、有关系、能导航

Phase 4: 智能引擎 (4-5 周)
- 摄取服务：文件/URL/文本上传
- 编译引擎：LLM 提取 - 生成 Wiki 页面
- 查询引擎：自然语言 - 图谱/搜索
- 一致性检查：orphan/stale/conflict 检测
- 输出：能自动从资料生成结构化知识

Phase 5: 记忆系统 (3-4 周)
- 记忆写入：Working - Episodic - Semantic
- 记忆衰减：Effective Importance 计算
- 记忆查询：向量 + 关键词 + 图谱混合
- 记忆整合：自动合并重复/过期记忆
- 输出：Agent 有持久、可检索的记忆

Phase 6: 生态集成 (2-3 周)
- MCP Server：stdio/sse 接口
- 导入导出：Markdown/JSON/Obsidian
- 图谱可视化：Cytoscape.js 交互图
- 输出：可接入外部 Agent，数据可迁移

Phase 7: 优化打磨 (持续)
- 性能：查询优化、缓存策略、CDN
- 安全：审计日志、数据加密、备份
- 体验：移动端适配、快捷键、主题
- 输出：生产就绪的系统

第五部分：风险管理

5.1 风险登记册

风险 | 概率 | 影响 | 应对策略 | 触发条件
LLM API 成本过高 | 中 | 高 | 支持本地模型（Ollama） | 月账单 > 100美元
协作编辑冲突频繁 | 中 | 中 | 增加锁机制 | 冲突率 > 5%
数据库性能瓶颈 | 低 | 高 | 读写分离、分片 | 查询 > 500ms
团队人员变动 | 中 | 高 | 文档完善、知识共享 | 核心人员离职

5.2 应急预案

场景：LLM API 不可用

1. 检测：API 调用失败率 > 10%
2. 切换：自动降级到本地 Ollama
3. 通知：发送告警到开发者
4. 恢复：API 恢复后自动切换回主服务
5. 复盘：记录故障原因，优化容错

场景：数据库数据损坏

1. 检测：数据校验任务失败
2. 隔离：停止写入，切换到只读模式
3. 恢复：从备份恢复（RPO < 1 小时）
4. 验证：数据完整性检查
5. 复盘：分析原因，加强监控

总结：项目成功的关键

1. 目标锚定：每个功能都回溯到用户场景，不为了技术而技术
2. 渐进交付：每 2 周一个可演示的里程碑，及时获取反馈
3. 分层验证：每层设计经过"定义 - 评审 - 原型 - 测试"四步
4. 决策记录：所有重要决策写入日志，避免反复讨论
5. 债务管理：技术债务及时记录，定期偿还
6. 度量驱动：用数据说话，不凭感觉决策
