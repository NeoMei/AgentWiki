## 一、从头写的陷阱：你不知道你不知道什么

### 1.1 需求层级落差

| 层级 | 你的表述 | 实现时必须回答 |
|------|---------|--------------|
| 愿景 | "Agent 团队共享知识" | — |
| 功能 | "Agent 可以编辑 Wiki" | Agent 怎么认证？编辑权限怎么控制？编辑冲突怎么处理？ |
| 细节 | ? | 并发编辑用乐观锁还是悲观锁？版本历史保留多少？Agent 编辑是否需要审批？ |
| 边界 | ? | Agent 删除页面怎么办？循环引用怎么检测？写坏数据怎么回滚？ |

**核心问题**: 从头写时，这些细节都需要你自己定义，但人的认知有盲区。

### 1.2 改造的优势：代码就是活的需求文档

Docmost 已经回答了：
- 并发编辑用 Yjs CRDT 方案
- 权限用 RBAC + 空间隔离
- 版本历史用 diff + snapshot
- 文件上传用 S3/本地存储抽象
- 搜索用 PostgreSQL FTS

**这些细节经过 2 万+ stars 社区验证**。

## 二、提示词指导的可靠性对比

### 2.1 从头写的提示词风险

| 风险 | 说明 | 例子 |
|------|------|------|
| 需求遗漏 | 提示词没提到，AI 不知道要做 | "支持 Agent 协作" -> AI 做了简单 API，没做并发控制 |
| 边界条件 | 提示词没覆盖异常场景 | "Agent 可以编辑页面" -> 没处理同时编辑同一页面 |
| 一致性 | 多次提示词可能矛盾 | 第一次说 "Agent 独立权限"，第二次说 "继承人类权限" |
| 可维护性 | AI 生成代码风格不一致 | 不同模块由不同 AI 会话生成，接口混乱 |
| 测试覆盖 | AI 不会主动写全面测试 | 只写 happy path，没覆盖错误处理 |

### 2.2 改造的提示词优势

| 优势 | 说明 |
|------|------|
| 既有代码约束 | "在 Docmost 的 page 模块上加 frontmatter 字段" -> 范围明确 |
| 模式参考 | "参考 Docmost 的 auth 模块，给 Agent 加 API Key" -> 有模板 |
| 边界已知 | Docmost 已处理大部分边界，你只处理新增部分 |
| 测试基线 | 既有测试确保你不破坏现有功能 |

## 四、修正建议：渐进式改造 + 退出策略

### 推荐方案

**改造 Docmost，但制定退出策略**

Phase 1 (2-3 周): 最小改造
- 在 Docmost 上加 Agent 认证 (API Key)
- 加页面类型字段 + 简单 Frontmatter
- 目标: Agent 能读写 Wiki，人类能审批

Phase 2 (3-4 周): 知识图谱
- 新增 knowledge_edges 表
- 加页面关联推荐
- 目标: 页面间有关系，能导航

Phase 3 (4-5 周): 编译引擎
- 异步摄取任务队列
- LLM 集成 (ingest -> compile)
- 目标: 能自动从资料生成 Wiki

Phase 4 (3-4 周): Agent 记忆
- 记忆表 + 衰减算法
- Agent 上下文构建
- 目标: Agent 有持久记忆

Phase 5 (2-3 周): 完善
- MCP Server
- 图谱可视化
- 性能优化

**总时间**: 14-19 周

**退出策略**: 如果 Phase 2-3 发现 Docmost 架构限制太大，用已验证的需求理解，从头重写核心模块。

## 五、功能定义清单（无论选哪条路都需要）

### 认证授权
- Agent 怎么注册？谁有权限注册？
- API Key 怎么生成？怎么轮换？
- Agent 权限粒度：空间级？页面级？操作级？
- Agent 操作是否需要人类实时审批？还是事后审计？

### 协作编辑
- Agent 和人类同时编辑同一页面怎么办？
- Agent 的编辑是否自动保存？是否需要草稿？
- 编辑冲突怎么解决？

### 知识图谱
- 关系类型有哪些？谁定义？
- 关系是自动提取还是手动创建？
- 关系有置信度吗？怎么更新？

### 编译引擎
- 什么触发编译？定时？事件？手动？
- 编译结果需要人类审批吗？
- 编译失败怎么处理？

### 记忆系统
- 记忆怎么触发写入？Agent 主动？系统自动？
- 记忆怎么衰减？什么策略？
- 记忆怎么查询？向量？关键词？图谱？
