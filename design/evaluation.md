# 从头写 vs 改造 Docmost：全面评估

## 一、核心需求拆解

| 需求 | 复杂度 | 是否 Docmost 已有 |
|------|--------|-------------------|
| 用户认证 (OAuth2/SSO) | 中等 | ✅ 已有 |
| 多用户协作编辑 | 高 | ✅ 已有 (Yjs) |
| 权限系统 (空间/页面级) | 高 | ✅ 已有 |
| Markdown 编辑器 | 高 | ✅ 已有 |
| 文件上传/管理 | 中等 | ✅ 已有 |
| 全文搜索 | 中等 | ✅ 已有 |
| 评论/讨论 | 中等 | ✅ 已有 |
| **Agent 认证 (API Key)** | **中等** | **❌ 需新增** |
| **页面类型 + YAML Frontmatter** | **低** | **❌ 需扩展** |
| **知识图谱 (4层图模型)** | **极高** | **❌ 需新增** |
| **摄取/编译引擎 (Karpathy)** | **极高** | **❌ 需新增** |
| **Agent 记忆系统 (4层)** | **极高** | **❌ 需新增** |
| **MCP Server** | **中等** | **❌ 需新增** |
| **Agent 审批工作流** | **中等** | **❌ 需新增** |
| **图谱可视化** | **高** | **❌ 需新增** |

**结论**: Docmost 覆盖了约 50% 的基础功能，但核心差异化功能（知识图谱、编译引擎、Agent 记忆）都需要从零构建。

## 六、最终建议

### 🟢 强烈建议：从头写

**核心理由**:

1. **核心差异化功能占 60%+ 工作量** — 这些都需要从零构建，改造带来的"基础功能"优势被稀释
2. **架构不匹配** — Docmost 是传统 Wiki，你的需求是 Agent-Native 知识系统，架构哲学不同
3. **技术栈可以更现代** — Next.js 15 + Server Actions + Prisma + pgvector 比 NestJS + 传统 REST 更适合 AI 应用
4. **无历史包袱** — 不需要理解/维护别人的 2 万行代码
5. **AGPL 限制** — 改造后必须开源，从头写可自由选择 License

### 如果一定要改造

唯一合理的场景：
- 团队完全不懂 React/Next.js，但熟悉 NestJS
- 需要 1 个月内出 MVP，且能接受简陋版
- 有专职维护团队处理 Docmost 升级合并

## 七、推荐技术栈（从头写）

| 层 | 技术 | 理由 |
|----|------|------|
| 前端 | Next.js 15 (App Router) | Server Actions 减少 API 层，React Server Components 性能 |
| UI | Tailwind + shadcn/ui | 快速构建，Agent 风格暗色主题 |
| 编辑器 | Milkdown / TipTap | Markdown 原生，可扩展 YAML Frontmatter |
| 协作 | Yjs | 成熟方案，与 TipTap 集成好 |
| 后端 | Next.js API Routes + Server Actions | 简化架构，减少层间通信 |
| ORM | Prisma | 类型安全，迁移方便，支持 pgvector |
| 数据库 | PostgreSQL + pgvector | 向量搜索，JSONB 灵活 |
| 缓存 | Redis | 会话、锁、队列 |
| 任务队列 | BullMQ (Redis) | 摄取/编译异步任务 |
| 图谱 | 自研 + Cytoscape.js | 轻量，可控 |
| LLM | OpenAI SDK / Ollama | 多提供商支持 |
| 部署 | Docker + Coolify / Railway | 自托管友好 |
