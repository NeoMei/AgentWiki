# Space 创建后不可见修复设计

## 背景与根因

Dashboard 当前调用 `GET /spaces` 时未传分页参数，因此服务端只返回默认前 20 条记录。`SpaceService.findAll` 同时没有稳定排序。超管可访问全部 Space；当测试数据超过 20 条时，刚创建的 Space 可能不在第一页。创建请求成功后弹窗会关闭，但随后的列表刷新以及浏览器手动刷新仍可能看不到新记录。

这不是 `edit` 权限问题。`POST /spaces` 只允许人类身份创建，并把创建者直接写为新 Space 的 `owner`；超管也是合法的人类身份。

另有一个独立但相关的可用性问题：创建失败错误目前显示在 Dashboard 顶部，创建弹窗会遮住错误，因此失败看起来像“点击后无反应”。

## 目标

- 新 Space 创建成功后立即显示在 Dashboard 顶部。
- 页面刷新后，新 Space 仍稳定显示在第一页。
- 超过 20 个 Space 时可继续加载其余记录，不丢失访问入口。
- 创建失败时在弹窗内显示本地化错误，并允许重试。
- 保持现有权限边界：人类用户可创建并成为 owner，Agent 不可创建；不引入 `edit` 权限要求或超管特例。

## 服务端设计

`SpaceService.findAll` 使用确定性排序：

1. `createdAt desc`
2. `id desc` 作为同一时间戳下的稳定游标顺序

现有 `skip` / `take`、最大 100 条限制和返回结构保持不变。第一页因此始终包含最新创建的 Space。

新增服务测试，验证默认分页查询带上述排序，并验证返回的 `total` 仍代表全部可访问 Space 数量。

## 前端设计

Dashboard 将列表加载拆分为“重置第一页”和“加载下一页”两种路径：

- 初始加载请求 `skip=0&take=20`，保存 `data` 与 `total`。
- “加载更多”请求以当前已加载数量为 `skip`，将结果按 id 去重后追加。
- 当已加载数量达到 `total` 时隐藏“加载更多”。
- 避免重复加载；加载更多失败时保留已有列表并显示错误。

创建成功后，以 `POST /spaces` 的响应为权威结果：

- 按 id 去重后插入列表顶部。
- `total` 增加 1。
- 清空表单并关闭弹窗。
- 不再要求第二次 GET 成功才能看见创建结果。

创建失败时：

- 弹窗保持打开。
- 在表单内显示本地化错误。
- 恢复创建按钮，允许修改信息后重试。
- 打开弹窗和重新提交时清除陈旧错误。

## 错误与并发

- 创建按钮在请求期间禁用，阻止重复提交。
- 加载更多按钮在请求期间禁用。
- 分页结果按 Space id 去重，防止创建与分页请求交错时产生重复卡片。
- 继续使用共享 `apiErrorMessage`，不向用户暴露服务端内部英文消息。

## 测试与验收

### 自动化测试

- 服务端：`findAll` 使用稳定的新到旧排序和正确分页参数。
- 客户端：创建成功后立即把接口返回的 Space 放在顶部，不额外依赖刷新。
- 客户端：总数超过 20 时显示“加载更多”，点击后追加并去重。
- 客户端：创建失败错误在弹窗内可见，按钮恢复可用。
- 服务端控制器：人类超管可创建且使用自己的 `userId`；Agent 仍被拒绝。

### 浏览器验收

目标流程：`/dashboard` → 创建 Space → 弹窗关闭 → 新卡片立即出现在顶部 → 刷新后仍在第一页。

同时检查超过 20 条时的“加载更多”、错误态可见性、控制台错误和中英文文案。

## 不做

- 不修改 Space 角色模型。
- 不赋予超管额外的 `edit` membership。
- 不取消服务端分页上限。
- 不在本轮推送、合并或部署生产。
