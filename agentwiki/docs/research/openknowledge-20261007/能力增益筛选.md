二者均存在收益假设，尚未用真实 Agent 对照实验验证。先建立任务基线，再决定具体实现；现有工具足够时，优先改进 Agent 使用指引。

## 1. 检索方向：先验证真实任务收益

典型任务：Agent 回答某项既有设计决策的原因，找到相关限制与来源，并据此提出修改；另一个 Agent 接手时，不必重新遍历全部资料。

借鉴 OpenKnowledge 的“搜索→读取→沿链接补查”循环，以及读取时附带关联信息的做法。官方资料说明了机制，未提供本项目上的收益证据：

- https://openknowledge.ai/docs/reference/agentic-search
- https://openknowledge.ai/docs/features/skills/built-in-skills

实现选择按成本递进：

1. 先改进现有 MCP 工具描述及 Agent 使用指引，验证现有接口能否完成任务。
2. 只有发现反复遗漏来源、关系或上下文组合成本过高，才增加精简的关联读取或上下文组合能力。
3. 不预先替换现有搜索、向量或图谱系统，不为借鉴重建一套知识存储。

基线任务需覆盖跨页决策、同名或相似内容、过期与新结论并存、找不到答案以及无权来源。测试至少使用两个独立 Agent 会话，覆盖知识复用而非原会话短期记忆。对照保持模型、工具预算及知识版本一致；记录多个运行结果，不以一例成功判断提升。

选型前固定通过门槛：正确性与可核对引用优先；耗时或上下文下降不能以遗漏关键限制为代价。若收益不足以覆盖额外维护成本，停止扩展接口。

## 2. 生命周期方向：聚焦可追踪来源

这部分是结合 AgentWiki 来源版本、Evidence、ChangeSet、审核及发布链路提出的适配方向，不能宣称 OpenKnowledge 已交付同样的完整闭环。

首期只处理能够证明来源关联的变化。来源发生变化意味着需要复核，不自动等于原结论错误；没有足够来源关联时明确标记覆盖不足，不伪造精确影响分析。

读取应能区分当前、待复核和已被替代的知识。更新沿用既有提案、权限与版本检查，不自动覆盖正式页面。需要区分“正确但不再适用”与“审核未通过”，不能把工作流状态当作事实有效性。

对照场景：来源中的一项明确事实发生变化，所有直接关联页面能被定位；无关页面保持正常。Agent 收到旧内容时识别其状态并查证，而非静默当作当前事实。审阅更新后，另一个 Agent 能取得更新结论，且可追溯替换原因和旧版本。

## 3. 提案质量检查：作为配套

只保留能帮助纠正知识内容的问题：重复结论、与已有证据冲突、来源缺失或失效。输出应包含对应旧知识或来源以及具体问题，供已有审阅流程使用。

OpenKnowledge 的内容规则会向 Agent 返回结构化告警，并可随写入响应返回检查结果。这是反馈机制的借鉴依据，不证明它能自动判断事实真假：

- https://openknowledge.ai/docs/advanced/content-rules/overview

字段校验、格式 lint、通用分数不单独成为下一阶段项目；语义判断只是需核验的建议，不能作为自动发布的证明。不新增一套审批系统。

## 实施顺序建议

先建立真实 Agent 使用现有知识的基线，同时核对来源关联覆盖。优先实现证据最充分、可观察到明显问题的一小段链路，再重复相同任务评估。检索与生命周期在产品价值上均为核心；具体排期由基线暴露的主因决定，不同时铺开两套大型系统。

所有新增读取继续使用明确 Space 范围和现有实时授权；来源失权后不返回正文、摘要或关系中的敏感内容。跨 Space 不增加统一通行凭据。
